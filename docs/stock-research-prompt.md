## 1. 核心設計原則（最重要，所有模組都要遵守）

1. **數字由程式計算，LLM 只負責解讀。** LLM 永遠不能自行產生股價、財務數字或比率。
2. **資料沒抓到、過期或異常，就明確報錯（fail loudly）。** 不可以靜默使用舊資料或預設值。
3. **LLM 的每個結論都要能追溯到來源**，並由程式自動驗證引用是否真實存在。
4. **不做股價預測。** 不輸出「會漲／會跌」、目標價、買賣建議、或「X% 機率上漲」這類數字。
5. **風險指標一律標註為「歷史統計值」**，不是未來機率。
6. **不偷看未來（no look-ahead）**：任何分析只能使用「在分析基準日當時已經公告」的資料（見 3.3）。
7. **所有報告結尾都要附免責聲明**：本工具僅供研究，不構成投資建議。

## 2. 市場範圍

### 2.1 主要市場：台股
- 上市（TWSE）與上櫃（TPEx）普通股。ETF、權證、興櫃、存託憑證（TDR）、特別股第一版不處理（第二階段再評估 ETF）。
- 代號格式統一為內部格式 `2330`，並記錄市場別 `TWSE` / `TPEX`。轉換給 yfinance 時分別用 `2330.TW` / `6488.TWO`。
- 幣別：新台幣（TWD）。
- 基準指數：優先使用發行量加權股價報酬指數（含息），因為個股報酬是用還原權息價格計算，兩者基礎才一致。若取不到含息指數，改用還原權息後的 0050，並在報告註明。不可用不含息的 TAIEX 搭配含息的個股報酬。

### 2.2 次要市場：美股
- 架構要能支援，但第一版只做台股。美股放在第 18 節的擴充階段，資料源改為 SEC EDGAR 與 yfinance、基準改為 SPY。
- 所有市場相關設定（交易日曆、漲跌幅、門檻、基準指數、無風險利率）放在 `config.yaml` 的 `markets.tw` / `markets.us` 底下，不可寫死。

### 2.3 台股特性（實作時必須處理）
- **漲跌幅限制**：2015-06-01 起為 ±10%，之前為 ±7%。新上市（櫃）前五個交易日無漲跌幅限制。
- **除權息**：台股配息比例高，所有報酬率、波動度、回撤一律用**還原權息價格**計算；顯示給使用者的現價用原始價格。兩者不可混用。
- **會計準則**：2013 年起採用 IFRS，之前為我國舊會計準則，兩者財報數字不可直接比較。
- **月營收**：每月 10 日前公告上月營收，是台股特有的重要資料。
- **財報公告期限**：年報（Q4）次年 3 月底前，Q1 / Q2 / Q3 分別約 5/15、8/14、11/14 前（以主管機關規定為準，期限放 config）。
- **休市**：國定假日、春節封關，以及**颱風假臨時休市**。
  - 歷史交易日：以官方資料中**實際有加權指數收盤**的日期為準，這樣過去的颱風休市自然會被排除，不需要另外維護清單。
  - 今天與未來：以證交所公告的休市日為準，臨時休市要能手動加入 config。
- **股票分割／面額變更**：部分公司採非 10 元面額或做過分割，每股數據要用調整後股數計算。

## 3. 資料來源

### 3.1 來源優先順序

| 優先 | 來源 | 用途 |
|---|---|---|
| 1 | 臺灣證券交易所 OpenAPI、證櫃買中心（TPEx）公開資料 | 日成交資料、本益比／殖利率／淨值比、交易日曆。OpenAPI 多數只提供近期資料，歷史資料若需使用證交所網站的歷史查詢端點，要遵守其使用規範並限速 |
| 1 | 公開資訊觀測站（MOPS） | 財報、月營收、股利、重大訊息、年報與法說會簡報（給 LLM 讀的文字） |
| 2 | FinMind API | 統一格式的股價、還原股價、財報、月營收、股利、除權息、新聞；方便開發 |
| 3 | yfinance（`.TW` / `.TWO`） | 第二個股價來源，用於交叉比對 |
| 參考 | Goodinfo!、Yahoo 奇摩股市、CMoney、鉅亨網等主流網站 | **人工核對用**：報告中附上這些網站的對應頁面連結，讓我自己點進去核對 |

規則：
- 主流網站**預設不自動爬取**。若要爬，必須先檢查該網站的使用條款與 `robots.txt`，確認允許後再實作，並加上速率限制與快取；不允許就只放連結。
- FinMind 有請求次數限制（免費版每小時數百次）與每週維護時段，且限非商業用途；要實作快取、限速、遇到維護時明確報錯。
- 官方來源與 FinMind 數字不一致時，**以官方為準**，並記錄差異。
- 「同產業中位數」需要抓整個產業的資料，請求量大：產業資料每期只抓一次並快取，所有個股共用；超過速率限制時排隊等待，不可跳過公司（跳過會讓中位數失真）。

### 3.2 快取
- 所有抓下來的原始資料存在本地快取（SQLite 或 parquet），記錄抓取時間與來源。
- 測試不打真實 API，一律使用 fixtures。

實作時確認的來源限制（使用者已同意）：
- 還原權息價格由程式依除權息、減資、分割的參考價計算（因數 = 參考價 ÷ 前一日收盤價），不使用 FinMind 付費的還原股價；`as_of` 之後的事件不套用。
- 股價只使用 2003 年起的資料（FinMind 參考價與加權報酬指數的起點），更早的價格無法正確還原。
- 上市前的興櫃交易資料一律剔除；上市日由資料推得，上櫃股票與櫃買中心官方上櫃日比對，推不出時放 config 手動指定。
- 減資、分割、面額變更前的停止買賣期間由事件資料推得，視為已知停牌。

### 3.3 時點正確性（point-in-time，防止偷看未來）
- 每一筆財務資料都要記錄兩個日期：`period_end`（資料所屬期間，例如 2019Q4）與 `available_date`（實際公告日）。
- 公告日取不到時，用該期的法定公告期限當作保守估計，並標記 `available_date_estimated = true`。
- 財報若曾重編（restatement），保留**原始公告版本**與重編版本；做時點回推時只能用當時的版本。若資料來源只提供最新版本、無法取得原始版本，要在資料健康報告與第 14 節的驗證結果中明確寫出這個限制。
- 從現在起，每次抓到的財報都存成不可覆寫的快照，往後就能累積真正的時點資料。
- 所有分析函式都接受 `as_of` 參數（預設今天），只能看到 `available_date <= as_of` 的資料。這是第 14 節驗證計畫的基礎。

## 4. 時間範圍、三個分析版本與新舊權重

### 4.1 資料抓取範圍
- 抓取所有可取得的歷史資料。
- 分界日 `REGIME_SPLIT_DATE = 2020-01-01`（疫情前後分界，可在 config 調整）。
- **財報類資料的最早起點為 2013 年（IFRS）**。2013 年前的財報不納入任何版本，因為會計準則不同不可比較。股價資料不受此限制。
- 報告中要顯示每個版本實際用到的日期範圍。

### 4.2 三個分析版本（time windows）

| 版本 | 名稱 | 股價資料範圍 | 財報資料範圍 |
|---|---|---|---|
| V1 | `post_2020` | 2020-01-01 至 `as_of` | 期間結束於 2020-01-01 之後，且已公告 |
| V2 | `full` | 最早可取得至 `as_of` | 2013 年起至 `as_of` 已公告 |
| V3 | `pre_2020` | 最早可取得至 2019-12-31 | 2013 年起、期間結束於 2019-12-31 前（含 2019Q4） |

**邊界規則**（避免歧義）：
- 財報數字依 `period_end` 分到 V1 或 V3。所以 2019 年報（2020 年 3 月公告）的**數字**屬於 V3。
- 但 **LLM 讀的文字資料**（年報文字、法說會、新聞）依**公告日**判斷：V3 只能讀 2019-12-31 前公告的文字。原因是 2020 年後公告的文件可能已經提到疫情，會讓 V3 偷看到疫情資訊。
- 因此 V3 的 LLM 質化分析使用的是 2018 年報（2019 年公告）及更早的文件。報告中要註明這點。

**各版本的角色**（依子期間穩健性檢查的學術慣例）：
- **V1 與 V3 是主要比較對象**，因為兩者時間不重疊。
- **V2 只當參考**，不參與判定。V2 包含 V1 的資料，拿來跟 V1 比較會高估一致性。
- V2 **不套用新舊權重**，顯示未加權的長期值。

實作要求：
- 做成一個 `TimeWindow` 物件傳進每個分析函式，**不能**為三個版本複製三份程式碼。
- 每個版本只能看到自己範圍內的資料，跨範圍洩漏要報錯。
- 某版本資料不足（例如公司 2020 年後才上市），該版本標為 `INSUFFICIENT_HISTORY`，不可以用其他版本的資料補。

### 4.3 越新權重越大（指數衰減）
- 權重公式：`weight = 0.5 ** (age_days / half_life_days)`
- `age_days` 相對於該版本的結束日計算：V1 為 `as_of`，V3 為 2019-12-31。V2 不加權。
- 半衰期依資料類型設定，可在 `config.yaml` 調整，預設：

| 資料類型 | 預設半衰期 | 套用方式 |
|---|---|---|
| 日報酬 | 90 天 | EWMA 波動度、加權平均報酬 |
| 月營收 | 1 年 | 加權年增率 |
| 季財報指標 | 2 年 | 加權 ROE、毛利率等 |
| 年度財報指標 | 3 年 | 同上 |
| 新聞 / 公告文字 | 30 天 | 決定送進 LLM 的排序與數量 |

- 報告中同時顯示「加權值」和「未加權值」。
- 加權值與未加權值在穩定性判定中的用法（避免混用）：
  - **數值指標**（第 5 節步驟 A、B 的經濟差距與統計檢定）：一律用**未加權值**。統計檢定需要原始樣本，而且未加權值不會因為權重設定造成假差異。
  - **投資框架的通過／未通過**（第 6 節）：每個版本用**該版本的加權值**判定（V2 用未加權值），再比較 V1 與 V3 的判定結果。因為 V1 與 V3 各自以自己的結束日為基準加權，兩者條件對稱，可以比較。

### 4.4 指標的取值方式（每個版本內）
- **年度或季度的財務指標**（ROE、毛利率、自由現金流等）：取版本範圍內各期數值的加權平均（V2 為簡單平均），並保留各期原始數值。
- **季節性處理**：季度資料一律用近四季合計（TTM）或與去年同期比較（YoY），不可直接比較不同季別的單季數字。月營收一律用年增率。
- **穩定性判定（第 5 節）優先用季度 TTM 資料**，因為資料點比年度多；季度資料取不到時才用年度資料。
- **TTM 跨越分界的處理**：TTM 只有在四季**全部**落在同一版本內時才屬於該版本。例如截至 2020Q2 的 TTM 包含 2019 下半年，不屬於 V1 也不屬於 V3，直接排除。因此 V1 的第一個 TTM 是截至 2020Q4，V3 的最後一個 TTM 是截至 2019Q4，第一個是截至 2013Q4。
- **估值類與「最近一期」類的時點指標**（本益比、殖利率、淨值比、股價、最近一季 EPS 年增率）：V1 取 `as_of` 當時的值，V3 取 2019-12-31 當時（已公告）的值，V2 同 V1。這類指標只有單一時點，不做統計檢定，一律帶 `LOW_SAMPLE` 標記。
- **股價與財報混合的指標**（例如「獲利成長是否高於股價成長」）：股價區間必須與財報區間對齊，不可一邊用 2013 起的財報、一邊用更早的股價。
- 送給 LLM 的文字一律**由新到舊排序**並附日期；超出 context 上限時優先捨棄最舊的。

## 5. 跨期穩定性判定（stability check）

方法依據：子期間穩健性檢查（subperiod robustness check）與結構性斷點檢定（structural break test），參考文獻見第 19 節。所有門檻放 `config.yaml`。

### 5.1 步驟 A：V1 vs V3 是否一致

每個項目同時看兩個條件：

**1. 經濟上的差距（差多少）**
- 一般數值（例如本益比、利息保障倍數）：相對差距 ≤ 15% 算差距小（`relative_tolerance`）
- **比率或百分比類指標**（ROE、毛利率、波動度、報酬率、殖利率）：改用**百分點差距**，例如 ROE 差距 ≤ 3 個百分點（各指標的 `absolute_tolerance` 分別設定）。原因是數值接近 0 時，相對差距會失真（例如 0.5% 對 1% 就差 100%）。
- 兩期數值正負號不同，直接判為差距大。
- 類別結果（通過／未通過、分類）：完全相同才算一致。
- 框架分數與綜合分數（0 到 1 之間的比例）：差距 ≤ 0.15 算差距小（`score_tolerance`）。

**2. 統計上的差異（是否顯著不同）**

只對下列指標做統計檢定，其他指標只看經濟差距：

| 指標 | 檢定方法 | 原因 |
|---|---|---|
| 日報酬平均 | Welch t-test | 兩期變異數不同時仍適用 |
| 波動度 | Brown-Forsythe test | Levene test 的中位數版本，較能承受股市報酬的厚尾 |
| Beta | 對基準指數回歸做 Chow test，使用 HAC（Newey-West）穩健標準誤 | 日報酬不符合同質變異假設 |
| 月營收年增率 | 迴歸加期間虛擬變數，使用 HAC 標準誤 | 相鄰月份的年增率高度相關，一般 t-test 會高估顯著性 |

- **財報類指標不做統計檢定**：TTM 數值相鄰期間重疊、高度自我相關，資料點也少，檢定結果不可靠。這類指標只看經濟差距，並標記 `ECON_ONLY`。
- 顯著水準預設 α = 0.05。
- **多重檢定校正**：一支股票同時做多項檢定，用 Benjamini-Hochberg 方法控制錯誤發現率，避免純粹巧合造成假的「不一致」。步驟 A 與步驟 B 的檢定各自為一組分別校正。

**最低資料量**（可設定）：
- 經濟差距：兩期各至少 2 個觀察值（季度 TTM 至少 4 季）
- 統計檢定：兩期各至少 60 個交易日（日資料）或 24 個月（月營收）
- 達不到經濟差距的最低資料量 → 該期視為資料不足
- 能算經濟差距但觀察值少於 8 個 → 加上 `LOW_SAMPLE` 標記

**一致的定義**：經濟差距小，**且**（有做檢定時）校正後統計上不顯著。兩者矛盾時判為不一致，報告中兩者都列出。

### 5.2 步驟 B：V1 內部是否穩定
- 把 V1 再切成前後兩段，用步驟 A 的方法比較。
  - **預設切點為 V1 期間的中點**（依 `as_of` 自動計算），不用固定日期。原因是第 14.4 節 walk-forward 驗證時 `as_of` 會逐月改變，固定切點可能讓後段幾乎沒有資料。config 可改成固定日期。
- **敏感度檢查**：V1 前段包含 2020 年疫情崩跌，可能讓指標看起來不穩定。所以另外跑一次排除崩跌期間的版本：
  - 股價類指標：排除 2020-02-20 至 2020-06-30（可設定）
  - 財報類指標：排除 2020 年度（年度指標），或排除包含 2020Q1、Q2 的 TTM 值（季度指標）
  - 只有在「含崩跌」與「排除崩跌」兩種算法都判定不穩定時，才算 V1 內部不穩定。
  - 報告中兩種結果都列出。
- V1 任一段達不到步驟 A 的最低資料量時，步驟 B 結果為 `UNKNOWN`。

### 5.3 步驟 C：判定結果

| V1 vs V3 | V1 內部 | 判定 | 意思 |
|---|---|---|---|
| 一致 | （不需檢查） | ✅ `STABLE` | 疫情前後都成立，最可靠 |
| 不一致 | 穩定 | 🔄 `REGIME_SHIFT` | 疫情後特性改變但已穩定，以 V1 為準，但樣本較少 |
| 不一致 | 不穩定 | ⚠️ `UNSTABLE` | 結論不可靠 |
| 不一致 | `UNKNOWN` | ⚠️ `UNSTABLE` | 無法確認已穩定，保守處理 |
| V1 或 V3 資料不足 | — | ❔ `INSUFFICIENT` | 無法判定，不可當成 STABLE |

- 帶 `LOW_SAMPLE` 標記的判定，在報告中要明確標示信心較低。
- V2 的數值只列出來當參考，**不影響判定**。
- 請用明確的規則表實作，並為每一列寫測試。

### 5.4 輔助資訊：資料自己找的斷點
- 對日報酬，以及對基準指數的 beta 回歸，跑 **Quandt-Andrews（sup-F）檢定**，找出最可能的結構性斷點日期。
- 前後各修剪 15%（trimming）避免斷點落在資料兩端；臨界值必須使用 Andrews (1993) 的表，不能用一般 F 分配。
- 報告顯示：偵測到的斷點日期、是否顯著、與 2020-01-01 相差多久。
- 只是輔助資訊，**不改變判定**。

### 5.5 判定層級
1. 每個指標／每個檢查項目各自判定。
2. 每個投資框架彙整：取最差的結果（嚴重度 `UNSTABLE` > `REGIME_SHIFT` > `STABLE`），同時顯示各判定的項目數量。`INSUFFICIENT` 另外計數，不參與排序；若框架內全部項目都是 `INSUFFICIENT`，框架判定為 `INSUFFICIENT`。
3. 整體判定：同樣取最差，並列出造成 `REGIME_SHIFT` / `UNSTABLE` 的項目。

報告中並列顯示 V1 / V3 / V2(參考) 的數值、差距、校正後 p-value。

## 6. 投資框架

用**規則化檢查表**實作以下投資人的核心原則。每個框架都用 V1、V2、V3 各跑一次，再做穩定性判定。
請用自己的話描述原則，不要引用原文。所有門檻放 `config.yaml`。

**年數規則**：V1（2020 年後）與 V3（2013–2019 的 IFRS 財報）各自只有約 6–7 個年度。原則中要求「10 年」的條件，在 V1、V3 中改用「該版本全部可用年度，最少 5 年」判斷，並在報告中註明與原始原則的差異；V2 年數足夠時，用原始的 10 年條件判斷並列為參考。少於 5 年則為「資料不足」，不可用更少年數湊數。

**項目類型**：每個項目標記為以下其中一種：
- **計分項**：結果為通過／未通過／資料不足／不適用，計入框架分數。
- **資訊項**：只顯示數值或描述，**不計分**。所有 LLM 產生的質化判斷都是資訊項，避免 LLM 的錯誤影響分數。

**模糊條件的量化定義**（全部可在 config 調整）：
- 「近幾年」= 該版本最近 5 個年度
- 「逐年增加」= 近 5 年中，比前一年不減少的年數 ≥ 4
- 「持續創新高」= 近 12 個月中，至少一個月的營收創該版本範圍內新高
- 「年增率高於通膨」= 近 12 個月營收年增率的中位數 > 同期 CPI 年增率

### 6.1 台灣代表（權重較高）

**華倫（周文偉）**
- 計分：近 5 年 EPS 成長率高於同期股價漲幅（股價區間與財報區間對齊）
- 計分：月營收持續創新高，且年增率高於通膨（CPI 來源：主計總處，需符合時點正確性）
- 計分：股利逐年增加
- 計分（反向）：最近一季本業 EPS 比去年同期衰退未超過 30%（衰退超過 30% 為未通過，並在報告中警示）
- 資訊項：目前現金殖利率與 5%–6% 區間的相對位置

**股魚**
- 計分：本業獲利（營業利益）占稅前淨利 80% 以上（稅前淨利 ≤ 0 時為不適用）
- 計分：自由現金流 > 0
- 計分：利息保障倍數 > 20（無利息費用時視為通過，並註明）
- 計分：ROE > 8%
- 計分：營業利益率 > 0
- 計分：本益比（近四季 EPS）< 12
- 計分：現金殖利率 > 6%
- 資訊項：參考價「每股淨值 × ROE ÷ 產業期待 ROE」，產業期待 ROE 放 config（例如半導體 10%、成熟電子 8%、傳產 6%）
- 此框架**不適用金融股與營建股**，遇到時整個框架標為 `NOT_APPLICABLE`
- 估值項目描述的是「是否符合該投資人的估值標準」，報告中不可寫成買進建議

**陳重銘（存股）**
- 計分：獲利穩定（依上方年數規則，各年度稅後淨利皆為正）
- 計分：每年皆有發放現金或股票股利
- 計分：近 5 年獲利持平或成長（最近年度稅後淨利 ≥ 5 年前，且未連續兩年衰退）
- 計分：近 5 年平均營收成長率與平均 ROE 均高於同產業中位數（同產業資料同樣受版本範圍與時點正確性限制）
- 資訊項：是否屬於偏好產業（金融、民生必需品、電信）

### 6.2 國外代表（權重較低）

**Warren Buffett**
- 計分：ROE 加權平均 > 15%，且超過半數年度 > 15%
- 計分：負債權益比低於門檻（金融股不適用）
- 計分：自由現金流各年度中至少 80% 為正
- 資訊項：護城河（LLM 從年報判斷，必須附引用）
- 資訊項：目前本益比、淨值比在該版本歷史區間中的百分位（不做 DCF 目標價，避免變成預測）

**Benjamin Graham**
- 計分：本益比 × 股價淨值比 < 22.5
- 計分：流動比率 > 2（金融股不適用）
- 計分：各年度 EPS 皆為正

**Peter Lynch**
- 計分：PEG < 1（PEG = 本益比 ÷ 近 5 年 EPS 年複合成長率百分比；起點或終點 EPS ≤ 0、或成長率 ≤ 0 時為不適用，不可硬算）
- 資訊項：依成長率分類（緩慢成長／穩定成長／快速成長／景氣循環等）

**Charlie Munger**
- 計分：毛利率高於同產業中位數（金融股不適用）
- 計分：ROIC（投入資本報酬率）加權平均 > 門檻（預設 12%）
- 資訊項：反向思考，列出可能出錯的地方（LLM，必須附引用）

### 6.3 通用的邊界規則
- EPS ≤ 0 時，本益比無意義，相關項目標為 `NOT_APPLICABLE`。
- 股東權益 ≤ 0 時，ROE 與淨值比無意義，標為 `NOT_APPLICABLE` 並在報告中**特別警示**。
- 產業分類使用證交所／櫃買中心的產業別。
- 計分項的結果只能是：通過／未通過／資料不足／不適用。四者在報告中要明確區分，計分時「資料不足」與「不適用」都不計入分母。
- 計分項在 V1、V3 的通過／未通過比較，就是第 5 節的「類別結果」；任一版本為資料不足或不適用時，該項穩定性為 `INSUFFICIENT`。

### 6.4 框架分數與權重
- 每個框架分數 = 通過項目數 ÷（通過 + 未通過項目數）。分母為 0 時框架分數為 `N/A`。
- 綜合分數 = 各框架分數的加權平均。`N/A` 的框架不計入，權重重新正規化的方式：
  1. 先在**群組內**正規化（例如股魚不適用時，華倫與陳重銘各占台灣群組的一半）
  2. 再依群組權重（台灣 60%、國外 40%）合併，維持「台灣代表權重較高」
  3. 若某一整個群組都是 `N/A`，綜合分數只用另一群組，並在報告中註明
- 預設權重（放 config，可調）：

| 群組 | 群組權重 | 群組內分配 |
|---|---|---|
| 台灣代表 | 60% | 華倫、股魚、陳重銘 各 20% |
| 國外代表 | 40% | Buffett、Graham、Lynch、Munger 各 10% |

- 綜合分數只描述「符合這些投資人原則的程度」，**不是買賣建議**，報告中要寫明。
- 綜合分數也要用 V1 / V3 比較並給出穩定性判定。
- 報告中同時顯示「只看台灣代表」與「只看國外代表」的分數，方便比較權重的影響。

## 7. 資料驗證（data/validation.py）

自訂例外類別（例如 `StaleDataError`、`MissingDataError`、`AnomalyError`、`SourceMismatchError`、`LookAheadError`），每個都要包含 ticker、欄位、實際值、預期條件。

檢查項目：
- **新鮮度**（只在 `as_of` 為今天時檢查）：最新收盤資料應為最近一個交易日。依台股交易日曆判斷，週末、國定假日、颱風休市不可誤報。盤中時段以前一交易日為準。
- **完整性**：價格、成交量不可為 null、NaN、負數；價格不可為 0。偵測交易日序列中間的缺漏。成交量為 0 但有價格，標記為「無成交」而非錯誤；成交量為 0 且所有價格都沒有（來源顯示 `---`）也視為無成交。
- **已知停牌**：`config.yaml` 維護一份停牌清單（代號、起訖日、原因）。清單內的日期缺資料視為正常，在資料健康報告中列出；清單以外的缺漏仍然報錯。
- **漲跌幅檢查**：原始收盤價單日漲跌超過當時的漲跌幅限制（2015-06-01 前 7%、之後 10%，加上 0.5% 的四捨五入容許）就報錯。例外：新上市（櫃）前五個交易日、除權息日（以參考價計算）、減資或分割後恢復交易日。
- **交叉比對**：官方、FinMind、yfinance 的**原始**收盤價互相比較，差距超過 0.5% 就報錯。只比對最近 60 個交易日（可設定），並跳過有分割、減資、面額變更的期間，因為部分來源會回溯調整歷史價格。還原價格不做跨來源比對，因為各來源的還原方式不同。
- **財報一致性**：資產 ≈ 負債 + 股東權益，誤差超過門檻就警告。
- **月營收合理性**：單月營收為 0 或年增率絕對值超過 500% 時標記可疑，要求人工確認。
- **版本範圍與時點**：資料超出 TimeWindow 範圍，或 `available_date > as_of`，就丟出 `LookAheadError`。

每次執行產生一份「資料健康報告」：每個來源的抓取時間、資料最新日期、通過／失敗的檢查項目。

## 8. 風險指標（analysis/risk.py）

全部使用**還原權息價格**，V1 / V2 / V3 各算一次：
- 年化波動度（簡單版；V1、V3 另附 EWMA 加權版）
- 最大回撤（含發生期間）
- Beta（對 2.1 設定的基準指數）
- 歷史 VaR 95%（單日）
- Sharpe ratio（無風險利率：使用各版本期間內的一年期定存利率平均值，因為 V3 期間的利率與現在不同；資料來源為中央銀行統計，取不到時用 config 中的分期設定值，並在報告註明）

報告中每個指標旁標註：「歷史統計值，計算期間 YYYY-MM-DD 至 YYYY-MM-DD，不代表未來機率」。
並註明各版本是否涵蓋重大事件（2008 金融海嘯、2015 漲跌幅放寬、2020 疫情崩跌、2022 升息與台股修正），因為這會大幅影響回撤與 VaR。

## 10. LLM 層與防幻覺（llm/）

LLM 只做三件事：
1. 從年報、法說會簡報、重大訊息中摘要重點與風險
2. 質化判斷：護城河、反向思考
3. 用白話繁體中文解釋程式算出來的數字

防幻覺機制（全部要實作並有測試）：
- **只給資料、不靠記憶**：system prompt 規定只能根據提供的內容回答，資料沒有就回答「資料不足」。
- **結構化輸出**：pydantic schema，每個論點包含 `claim`、`quote`、`source_doc`、`source_date`。
- **引用驗證**：用程式檢查 `quote` 是否存在於來源文件。比對前先正規化：全形／半形統一、空白與換行移除、標點統一。**不做繁簡轉換**（來源本來就是繁體，轉換可能掩蓋 LLM 改字的情況）。PDF 抽出的文字要先檢查品質，抽取失敗的文件不送進 LLM。
- 驗證失敗的論點標為「未驗證」，從主要結論移除，但在報告附錄列出，不可直接刪掉不提。
- **數字驗證**：抽出 LLM 輸出中的所有數字（含中文數字、「億」「萬」等單位換算），與程式計算值或來源文件比對，不符就標記。
- 低 temperature（預設 0），重試一次後仍失敗就標為失敗。
- 每次呼叫記錄 prompt、回應、驗證結果到 log 檔。
- V3 只能讀 2019-12-31 前公告的文件（見 4.2）。
- 測試用 mock 的 LLM 回應（含故意捏造引用與數字的案例），確認驗證機制能抓到。
- LLM：Anthropic API，model 名稱放 config。

## 13. 單元測試要求

- 使用 pytest，**測試不可呼叫真實 API**，一律用 fixtures 或 mock。
- 必須涵蓋：
  - 每一種驗證錯誤都會被正確觸發
  - 漲跌幅檢查：2015-06-01 前後門檻不同；新上市前五日、除權息日不誤報
  - 台股交易日曆：週末、國定假日、颱風休市不誤報資料過期
  - 每個 TimeWindow 拿不到範圍外的資料；V3 的 LLM 文字只來自 2020 年前公告的文件
  - `as_of` 之後公告的資料無法被使用（`LookAheadError`）
  - 2013 年前的財報不進入任何版本
  - V3 權重以 2019-12-31 為基準；數值指標的穩定性判定使用未加權值，框架計分項用各版本的加權值判定
  - TTM 跨越 2020 分界時被排除，不屬於任何一個版本
  - 穩定性判定表每一列至少一個測試，另測：比率指標用百分點差距、正負號相反、經濟差距與統計檢定矛盾、BH 校正、`UNKNOWN`、`INSUFFICIENT`、最低資料量邊界、財報類指標不做檢定並標記 `ECON_ONLY`
  - 季節性：不同季別的單季數字不會被直接比較（一律 TTM 或 YoY）
  - 歷史交易日由官方指數資料推得，過去的颱風休市不會被當成資料缺漏
  - 框架權重：群組內先正規化、群組權重維持 60/40、整個群組 `N/A` 的處理
  - V2 的數值改變時，判定結果不受影響
  - 敏感度檢查：只有含崩跌與排除崩跌都不穩定時，才判定 V1 內部不穩定
  - 統計檢定：用模擬的「有斷點」與「無斷點」資料確認能正確區分；Quandt-Andrews 能在誤差內找回埋入的斷點
  - 投資框架：資料不足、不適用（金融股、EPS ≤ 0、負成長的 PEG、股東權益 ≤ 0）的處理
  - 框架分數：分母為 0、部分框架 `N/A` 時權重重新正規化
  - LLM 捏造引用、捏造數字（含中文數字與「億」單位）時能被抓到
  - 還原價格與原始價格不會混用
- 核心模組（validation、windows、calendar、weighting、risk、stability、breakpoints、frameworks、scoring、verification）覆蓋率目標 90% 以上。
- GitHub Actions：每次 push 跑 ruff + pytest。

## 14. 驗證計畫（確認工具判斷是否可信）

這一節是「工具做出來之後，怎麼證明它有用」。程式放在 `validation/`，結果存在 `validation/results/`。

### 14.1 工具判定與人類判斷的對應方式
專家和已知案例只會回答「有沒有改變」，工具則有四種判定，所以要先定義對應規則：
- 工具 `STABLE` → 「未改變」
- 工具 `REGIME_SHIFT` 或 `UNSTABLE` → 「有改變」
- 工具 `INSUFFICIENT` → 排除，不計入正確率或 kappa，但另外統計比例
- 面向層級（營收／獲利／風險）的工具判定 = 該面向指標中最差的判定：
  - 營收：月營收年增率、營收成長率
  - 獲利：ROE、毛利率、營業利益率、EPS
  - 風險：波動度、Beta、最大回撤
- 整體判定 = 三個面向中最差的判定

### 14.2 事前登記（最先做）
- 在跑任何驗證之前，先建立 `validation/preregistration.md`，寫下每項測試的**成功標準**，並 commit 進 git。
- 驗證結果出來後不可回頭修改成功標準；若要修改，新增一個帶日期的修訂段落並說明理由。
- 預設成功標準（我可以調整）：
  - 已知案例測試：判定正確率 ≥ 80%
  - 專家一致性：工具與專家多數決的 Cohen's kappa ≥ 0.6，或不低於專家之間 kappa 減 0.1
  - 逐月 walk-forward（第 14.4 節，以保留期結果為準）：判定為 `STABLE` 或 `REGIME_SHIFT` 的指標，後續標準化變動顯著小於 `UNSTABLE` 的指標（Mann-Whitney U，單尾，α = 0.05，顯著性以 block bootstrap 計算）；且工具的 AUC 高於基準 B（隨機判定）分布的 95 百分位
  - 報告盲評：工具報告的平均分數不低於人工報告 0.5 分以上（5 分制）

### 14.3 已知案例測試（成本最低，最先跑）
- 建立 `validation/known_cases.yaml`，由我（或專家）列出兩組台股：
  - 公認疫情後明顯改變的公司（例如受遠距需求、航運運價、AI 伺服器需求大幅影響者）
  - 公認長期穩定的公司（例如民生必需品、電信龍頭）
- 每支股票針對營收、獲利、風險三個面向，標註**預期是否改變**與理由，在跑工具之前就寫好。
- 工具跑完後產出混淆矩陣與正確率。
- 依 14.1 的面向對應計算，避免結果被大量次要指標稀釋。

### 14.4 逐月 walk-forward 驗證（含保留期）

目的：驗證「穩定性判定」準不準，不是預測股價。不可用股價漲跌當成功標準。

**1. 時間切分**（全部放 config）
- 預測期長度 H：預設 3 個月
- 開發期：基準日每月月底，從 2023-12-31 到 2025-06-30
- 隔離期：2025-07 到 2025-09 的基準日不使用，避免開發期的後續結果與保留期重疊（purging / embargo）
- 保留期：基準日從 2025-10-31 到 2026-06-30，後續結果最晚到 2026-09-30
- 規則：每個基準日 + H 必須 ≤ 今天，否則不納入

**2. 每個基準日的流程**
- 用 `--as-of <基準日>` 跑工具，只能用當時已公告的資料
- 記錄 14.1 指標的判定（STABLE / REGIME_SHIFT / UNSTABLE / INSUFFICIENT）
- 計算後續變動：
  - 股價類、月營收類：基準日之後 H 個月的值與基準日 V1 值的差距
  - 財報類：基準日之後下一次公告的 TTM 值與基準日 V1 值的差距
  - 標準化：差距除以該指標在第 5 節的容忍度

**3. 調參規則（只能用開發期）**
- 可調參數：容忍度、半衰期、V1 內部切點、崩跌排除區間
- 每一次嘗試的參數組合都要記錄到 `validation/results/tuning_log.csv`，包含嘗試次數，不可只留最好的結果
- 嘗試次數上限預設 30 組，避免過度調整
- 選參數時優先選「附近參數表現也差不多」的組合，而不是單一最佳點（穩健性優先於最佳化）

**4. 保留期規則**
- 開發期調參完成後，把最終參數與成功標準寫進 `preregistration.md` 並 commit，之後才可以跑保留期
- 保留期只能跑一次，結果直接記錄
- 保留期沒通過時，不可以根據保留期結果回頭調參再測。只能改用第 14.5 節的前瞻追蹤，等新資料累積後再驗證
- 用 hook 或程式檢查：preregistration commit 之前，禁止執行保留期驗證

**5. 比較基準（要贏過才算有效）**
- 基準 A：全部判定為 STABLE
- 基準 B：隨機判定，各判定的比例與工具相同（重複 1000 次取分布）
- 評估指標：
  - STABLE / REGIME_SHIFT 的後續標準化變動是否顯著小於 UNSTABLE（Mann-Whitney U，單尾）
  - 判定結果預測「後續變動超過容忍度」的 AUC
- 工具的 AUC 必須高於基準 B 分布的 95 百分位才算通過

**6. 統計注意事項**
- 每月基準日的預測期會互相重疊，結果不是獨立樣本。顯著性改用區塊自助法（block bootstrap，以股票和季度為區塊）計算，不可直接用一般檢定的 p-value
- 每個結果都附上樣本數與信賴區間

**7. 輸出**
- 每個基準日的判定與後續變動存成 `validation/results/walk_forward.parquet`
- 報告：開發期與保留期分開呈現、與兩個基準比較、調參嘗試次數
- 新增 CLI：`stock-research validation run walk-forward --phase dev` 與 `--phase holdout`

**8. 測試**
- 基準日 + H > 今天時不納入
- 開發期的後續結果不會跨進保留期
- preregistration 未 commit 時，holdout 指令會報錯
- 調參紀錄不會被覆寫
- block bootstrap 用模擬資料驗證結果合理

### 14.5 前瞻追蹤
- 每次正式執行分析時，把判定結果連同日期與 git commit hash 存檔到 `validation/forward_log/`（不可覆寫舊檔）。
- 提供指令在 6、12 個月後比對當初的判定與實際變化。

### 14.6 專家盲測標註
- 樣本：20–30 支台股，涵蓋不同產業與市值，包含 14.3 以外的股票。
- 專家：3–5 位資深股民。
- 流程：
  1. 用 `export-expert-forms` 產生評分表（CSV 或 Excel），**表上不顯示任何工具結果**。工具以發表單當天為 `as_of` 執行並存檔，確保專家與工具使用相同時點。
  2. 專家各自獨立填寫，不互相討論。
  3. 收回後用 `score-experts` 計算：專家之間的一致性（Fleiss' kappa，超過兩位評分者時使用）、工具與專家多數決的一致性（Cohen's kappa，依 14.1 對應）。專家意見平手時，該題不納入多數決。
  4. 專家之間的一致性就是工具的合理天花板。
- 評分表欄位：
  - 股票代號、名稱
  - 疫情後營運特性是否明顯改變（是／否／不確定）
  - 營收、獲利、風險三方面各自是否改變（是／否／不確定）
  - 護城河強度（強／中／弱／不確定）
  - 最主要的 3 個風險（自由填寫）
  - 判斷信心（1–5）
  - 填寫者投資年資、熟悉產業（匿名代號，不記錄真實姓名）
- 「不確定」不納入 kappa 計算，但另外統計比例。

### 14.7 報告品質盲評
- 挑 5–10 支股票，各準備兩份報告：工具產生的、人工撰寫的，統一格式並移除來源標記，順序隨機。
- 專家依以下面向 1–5 分評分：數字正確性、是否漏掉重要風險、論述是否有根據、實用性。
- 另請專家標出報告中他們認為錯誤的內容，用來統計錯誤率。

### 14.8 有工具 vs 沒工具
- 專家分析同一組股票，一半使用工具、一半不用（分配方式隨機並交叉輪換）。
- 比較花費時間與分析品質（品質由另一位不知情的專家評分）。

### 14.9 使用觀察
- 觀察專家實際操作，請他們邊用邊說出想法，記錄看不懂或不信任的地方，整理成改善清單。

### 14.10 要避開的陷阱（實作時要內建防護）
- **前視偏差**：walk-forward 的每個基準日一律透過 `as_of` 機制，禁止繞過；開發期與保留期之間保留隔離期。
- **過度調參**：只能用開發期調參並記錄每次嘗試；保留期只跑一次，未通過不可回頭調參。
- **倖存者偏差**：樣本用當時的名單。
- **錨定效應**：專家必須先獨立判斷，再看工具結果。
- **用股價漲跌當成功標準**：禁止。
- **事後才定義成功**：一律以 `preregistration.md` 為準。
- **樣本太少**：每個結果都要附上樣本數與信賴區間。

## 18. 階段規劃

1. **專案骨架**：結構、config、CLAUDE.md、測試框架、CI
2. **台股基礎**：代號格式、交易日曆（含颱風休市）、漲跌幅規則 + 測試
3. **資料層**：fetchers、快取、時點正確性、TimeWindow、完整驗證 + 測試
4. **分析層**：權重、基本面、月營收、風險指標 + 測試
5. **投資框架與分數**：七個框架、邊界規則、加權分數 + 測試
6. **穩定性判定**：V1 vs V3、V1 內部與敏感度、統計檢定、BH 校正、斷點偵測、規則表 + 測試
7. **LLM 層**：年報摘要、防幻覺驗證 + 測試
8. **報告與 CLI**
9. **Claude Code 設定**：skill、subagents、slash command、hooks
10. **驗證工具**：事前登記、已知案例、逐月 walk-forward（含保留期）、前瞻追蹤、專家評分表與計分
11. **擴充（選做）**：美股、ETF、HTML 報告、多股比較

若時間有限，第 6 階段可先做經濟差距與判定表，統計檢定與斷點偵測之後補上；但第 3 階段的時點正確性不可省略，因為第 10 階段的驗證依賴它。
